# コンポーネント境界とテスト対象の設計判断

## コンパイラを使う理由と保守コスト

関係を別ファイルに登録すると、実装の変更に追従する保守が必要になる。
コンパイラが解決した定義を使い、別名、再公開、マクロによる表記差で呼出先を取り違えないようにする。
同名の別メソッドを名前だけで結合する方式は採用しない。

解析は固定した Rust の内部 API に依存するため、ツールチェーンを更新する際に解析器の追従が必要になる。
この依存を解析用ツールに閉じ込め、製品の通常ビルドには nightly 機能を要求しない。

## テストの意図を明示する理由

API を呼ぶテストが、その API の振る舞いを検証するとは限らない。
セットアップの呼出と検証対象を区別するため、作者が `targets` 属性で意図を明示する。
具体的な実装を検証する意図と、trait のインターフェースを検証する意図も区別する。
通信の検証に便宜的なローカル API を割り当てない。

静的な呼出情報、対象の指定、テストの成功、契約を十分に検証することは別の情報である。
対象属性がないことだけでテストの不足とは判断しない。

属性の指定と生成の手順は[コンポーネント境界とテスト対象を生成する](../how-to/check-traceability.md)を参照する。
