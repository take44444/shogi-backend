# 対局時計

対局時計を既存の対局履歴、終局通知、レート処理に組み込む。
この設計は実装承認済みであり、時計モデル、永続確定、通信、自動判定を一つの変更として実装した。
ゲームスキーマは版9、通知JSONは版2を使用する。
旧版のDBを移行または削除せず、新しい空のDBで初期化する。

## 時計の仕様

| 項目 | 仕様 |
| --- | --- |
| 対象 | 既存プールの10分＋30秒読み、持ち時間なしの30秒読み |
| 開始 | 両者の準備確認により対局を作成するトランザクションで先手の計測を開始 |
| 時間の単位 | 内部計算、保存、通信は整数ミリ秒。秒未満の切り捨てはしない |
| 秒読み | 持ち時間を使い切った手から30秒を使える。着手ごとに30秒に戻る。加算はしない |
| 期限 | `判定時刻 >= 期限` で手番側の時間切れ負け |
| 着手の時刻 | 対局行のロック取得と状態確認後に取得したDB時刻。クライアント送信時刻は使わない |
| 通信遅延 | 補償を設けない。通信、キュー待ち、DBロック待ちは対局者の消費時間に含む |
| 切断 | 時計を止めない |
| サーバー停止 | 時計を止めない。復旧後に期限を過ぎた対局を終局させる |
| 終局 | 時計を停止し、最後の局面と確定した残り時間を保存 |

上記の遅延補償、停止中の扱い、秒未満の扱いはプロダクト上の選択である。
オンライン将棋の既存サービスと同一の運用を保証する仕様ではない。
障害時の無効対局や運営による時計調整は今回の対象に含めない。

## 既存処理との接続

[対局アクター](../../crates/game-application/src/actor.rs)は操作前に永続バージョンを確認し、履歴から局面を復元する。
[保存処理](../../crates/game-persistence/src/lib.rs)は操作、対局の結果、Outboxを同時に保存する。
終局時にはマッチメイキングの状態変更とレートジョブの受付も同じトランザクションに含まれる。

[準備確認](../../crates/game-persistence/src/matchmaking.rs)が両者分そろった時点で対局を作成しているため、時計もその時点で初期化する。
マッチ成立時や最初のWebSocket接続時を時計の開始には使わない。

現在の履歴、イベント、公開棋譜はユーザーの着手または投了を前提としている。
時間切れを投了として記録せず、システムが確定した別の履歴として拡張する。

## 二つの構成と推奨案

| 構成 | 特徴 | 判断 |
| --- | --- | --- |
| アクターがプロセス内タイマーを正本として持つ | ローカルでは直列になる。再起動時の復元と複数プロセス間の所有権管理が別途必要 | 今回は採用しない |
| DBに時計と期限を保存し、対局行をロックして確定する | 着手と時間切れを同じ保存状態に対して判定できる。再起動後も期限を検索できる | 推奨 |

時計の計算とイベント生成はアプリケーション層が担当する。
保存層はDB時刻、ロック、原子的な保存を担当する。
アクターは操作間の局面キャッシュを保持しない。
各操作でロックした履歴を復元し、複数プロセス間の排他はDBで保証する。
この構成は、時計と履歴を異なるバージョンで判断する経路を減らす。
開発用debugビルドの比較では、同じ合法手列の確定と最終局面を両構成で検証した。
同時実行のビルドとテストによる負荷があるため、この比較から本番性能の優劣を判断しない。
長い履歴の復元コストと本番のロック保持時間は、導入先の負荷検証で確認する。
毎秒の残り時間更新をDBへ書き込まない。

## 型と状態の所有者

以下は責務を示す型の概略であり、最終的なRustの宣言ではない。
時刻と期間には区別できる型を使い、数値の範囲は復元時にも検証する。

```text
TimeControl { initial_main_ms, byoyomi_ms }

ClockState =
    Running { main_remaining_ms: [black, white], turn_started_at, deadline_at }
  | Stopped { main_remaining_ms: [black, white], byoyomi_remaining_ms: [black, white], stopped_at }

JournalEntry =
    UserCommand { request, acceptance, evaluated_at, clock_after }
  | Timeout { seq, expected_seq, loser, deadline_at, evaluated_at, clock_after }

EventOrigin =
    User { request_id, user_id }
  | System
```

`game-application`の対局状態が局面、手番、時計をまとめて所有する。
時計に別の手番を持たせず、局面の手番を計算に渡す。
レートの`Pool`から対局作成時に`TimeControl`を選び、その値を対局に保存する。
後のプール定義変更で進行中の時計を変更しない。

`shogi-domain`には`FinishReason::Timeout`と、進行中の手番側を時間切れで終局させる操作を追加する。
ドメインは時刻取得や期限判定を行わず、アプリケーション層が期限確認後に呼び出す。
結果の所有者は既存の`Game`に統一し、別の終局フラグを追加しない。

## 計算規則

手番開始時の持ち時間を`M`、秒読みを`B`、開始時刻を`S`とする。
期限は`D = S + M + B`である。

- `T >= D`なら時間切れ。着手や投了を新しく受理しない。
- `T < D`で合法手を受理したら、手番側の持ち時間を`max(0, M - (T - S))`にする。
- 次の手番は`T`を開始時刻とし、相手の持ち時間と秒読みから期限を作る。
- 非合法手や古い要求による拒否では、開始時刻や期限を更新しない。経過時間はそのまま進む。
- 投了や詰みによる終局でも、その時刻までの手番側の消費時間を確定して時計を停止する。

停止時には、手番側の秒読み残量も`max(0, B - max(0, T - S - M))`として保存する。
相手側の秒読みは次の手番に使える全量を保持する。
時間切れの場合は残量を0、停止時刻を期限とし、検出した時刻は`evaluated_at`に別途残す。

例えば持ち時間が5秒残っている手では、35秒未満で着手できる。
10秒使って着手すると持ち時間は0秒になり、次回の手番では新たに30秒使える。
35秒ちょうどで判定された着手は時間切れになる。

DB時刻が直前に保存した時刻より戻った場合は、その保存時刻まで進めた値を使い、持ち時間の増加を防ぐ。
DB時計の大きな前進や停止は補償できないため、DB時刻の同期を運用前提とする。

## 着手と時間切れの確定

保存APIは、ロックされた対局とDB時刻をアプリケーション層へ渡し、その決定を同じトランザクションで保存できる契約に変更する。
現在の`commit_change`に別途時刻照会を付け足す形では、照会と保存の間に競合が残る。

概略の境界は`begin_game_update(id)`、`locked_record()`、`decision_time()`、`commit(change)`である。
トランザクションの実装型は保存層に閉じ込め、アプリケーション層にSeaORMの型を渡さない。
途中のエラーやキャンセルはロールバックし、ネットワーク通知はトランザクション外で行う。

1. 対局行をロックし、そのバージョンに対応する状態を得る。キャッシュを使う場合もロックしたバージョンとの一致を確認する。
2. 操作者の参加資格を確認し、受理済み要求の完全一致再送を調べる。一致なら保存済みの元の応答を返す。
3. 新しい操作ではDB時刻を取得する。進行中かつ期限到達なら、手番側の時間切れを確定する。
4. 期限前なら既存の順序で`expected_seq`、終局状態、手番、合法性を検証する。
5. 履歴、時計、バージョン、結果、Outbox、必要なレートジョブと参加状態を原子的に保存する。
6. コミット確認後に応答する。結果不明なら永続履歴を再取得する。

時間切れを確定した呼び出しでは、ユーザーの要求を受理済みとして保存しない。
呼び出し元には終局を示すエラーを返し、スナップショットの再取得で最終状態を取得させる。
すでに受理した着手の完全一致再送は、後に時間切れになっていても元の応答を返す。

時間切れも履歴の`seq`を一つ進める。
`seq`は受理したユーザー操作数から、システム終局を含む状態遷移数へ契約を変更する。
上限の最後の一枠は終局に使えるよう確保し、進行中のまま上限に到達する着手は拒否する。
履歴復元では保存した時刻と時計を検証し、現在時刻によって過去の結果を再判定しない。

既存の終局処理は共通のマッチメイキングロックを対局更新より先に取得する。
この順序を逆転させない。
通常の対局行ロック中に終局が必要と分かった場合は、一度ロールバックして共通ロック、対局行ロックの順に取り直す。
取り直した状態と時刻で再判定し、途中の候補は保存しない。
これにより通常の着手をすべて共通ロックで直列化することを避ける。

## 操作がない対局の時間切れ

`games`に時間設定、両者の持ち時間、手番開始時刻、現在の期限、停止時刻を保存する。
進行中の期限に部分インデックスを設ける。
履歴には復元に必要な判定時刻と確定後の時計を保存する。

`game-server`に期限検索の定期処理を追加する。
走査間隔は250ミリ秒、各回の候補は128件までとする。
この間隔はプロダクト設定であり、本番負荷の測定に基づく値ではない。
期限検索のDB時刻を一度取得して整数値で渡し、部分インデックスの範囲検索を使えるようにする。
一件の復元や保存が失敗しても、同じ取得バッチの残りを処理してからエラーを返す。
候補は上限付きで期限順に読み、保存時にロック下で期限と終局状態を再確認する。
検索時のロックを保持したまま別の確定トランザクションへ渡さない。
複数サーバーが同じ候補を取得しても、確定できるのは一つだけとする。
読み込み済みアクターがない対局も対象にする。

定期処理の遅延は終局通知を遅らせるが、期限を延ばさない。
期限後の着手や投了も、同じ時間切れ確定処理を通す。
再起動後は保存済み期限を検索して処理を再開する。

## 通信と公開棋譜

`Snapshot`に時間設定、時計状態、両者の持ち時間、手番開始時刻、期限、`server_now_ms`を追加する。
状態とサーバー時刻は同じ永続ビューに基づける。
終局がまだ定期処理で確定していない場合、期限を過ぎたスナップショットもあり得る。
表示は0秒までとし、勝敗の表示は保存済みの結果に従う。

`Acceptance`には受理時に確定した時計を追加し、完全一致再送でも同じ値を返す。
再送応答の時計は現在値ではないため、再接続時はスナップショットを取得する。
各確定イベントには、その遷移で保存した時計と`evaluated_at_ms`を付ける。
相手と観戦者もこのイベントの絶対期限で時計表示を更新する。
`evaluated_at_ms`は過去の判定時刻であり、現在時刻ではない。
Outboxの再試行で遅れて届いても、スナップショット由来の時刻差を更新しない。
毎秒の時計イベントは配信しない。
クライアントはスナップショットのサーバー時刻とローカルの単調時計を使って表示を進める。
通信遅延による表示誤差を勝敗判定には使わない。

`GameFinished`の既存イベント識別子`(game_id, seq, kind)`を維持する。
イベントの発行元は`EventOrigin`で表現し、時間切れに架空のユーザー要求IDを作らない。
Outbox、メッセージのエンコードとデコード、ゲートウェイ、公開棋譜の全経路に`Timeout`を追加する。
公開棋譜では時間切れを着手や投了に変換せず、最後の局面と別の終局として返す。
レートは既存の終局ジョブと適用台帳を使って一度だけ更新する。

## 実装と検証

時計計算と期限境界は`game-application`の単体テストで検証する。
PostgreSQL統合テストは、両プール、行ロック待ち、終局ロックの取り直し、複数サービスの競合、再起動後の履歴復元を検証する。
時間切れによる結果、システム履歴、Outbox、参加状態、レートジョブを同じトランザクションで保存する。
レートワーカーの適用台帳により、一対局のレート更新は一度だけになる。

実サーバーのテストは、接続のない期限切れ対局を起動時に処理し、再起動しても終局を重複保存しないことを検証する。
ゲートウェイのテストは、相手と観戦者への時計付き着手通知、時間切れ通知、再接続時の停止時計を確認する。
公開HTTPと読み取り専用DBのテストは、`timeout`検索と着手数に含まれない時間切れ履歴を確認する。

表示用フロントエンドはこのリポジトリに含まれない。
実際の時計表示と本番負荷での通知遅延は、導入先で確認する。
既存DBの移行、停止中の無効対局、運営による時計調整は実装しない。
旧版のwriter、reader、通知形式を混在させない。

## 設計判断に使った原則

Foundational Thinkingに従い、時刻、期間、時計状態、履歴の形を操作処理より先に決めた。
Model the Domainに従い、動作中と停止済みの時計、およびユーザー操作とシステム終局を型で区別した。
Prove It Worksに従い、PostgreSQL、Valkey、実サーバーで保存と通知の結果を検証する。
