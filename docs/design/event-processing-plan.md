# イベント配信と永続ジョブの将来設計

本書は今後追加する定期照合・並列配信、永続ジョブ、レーティングの設計方針であり、現行実装の保証ではない。
採用済みの保存・通知方式の理由は[イベント配信のADR](../adr/0003-game-event-delivery.md)、未実装項目の一覧は[未完成の機能](unfinished-work.md)を参照する。

## Gatewayの再同期と並列配信

現行 Gateway は購読断と検出した連番の欠落で接続を閉じ、再接続時に保存済み局面を送る。
最後の通知の欠落を後続の連番だけでは検知できないため、将来は定期照合も行う。
配信を並列化する際は、取得・担当管理・順序保証を別途設計する。

## 永続ジョブの取得と完了

将来の永続処理には、Consumer別のPostgreSQLジョブと完了状態を設ける。
ジョブは一意キー、所有者・世代を持つ期限付きclaim、再試行時刻・回数、隔離状態を持つ。
Workerは短いトランザクションでclaimし、長い処理の間はトランザクションを保持しない。

完了は処理結果のDB Commitを根拠とする。
同じDB境界の業務更新と完了記録は、有効なclaimを検証した同じトランザクションに含める。
別DB境界の完了記録は業務Commit後に行う。
再試行は業務側の一意制約・適用台帳でも冪等にする。

## DB境界をまたぐ受入

Game側の確定データとジョブを同じトランザクションで保存できる場合は直接保存する。
別DB境界では、送信元の専用Outboxから受信側の永続Inboxへ同じIDで渡す。
受信側はInboxとジョブを原子的に保存し、その耐久的な受入後に確認を返す。
送信側は確認後にだけ、その宛先への受入済み状態を記録する。

この受入済み状態も業務処理の完了とは区別し、一時通知用の受入状態とは共有しない。
Pub/Subの購読を永続ジョブへの中継元にしない。

## レーティングの順序と参加枠

Ratingは同じユーザー・poolで前局の反映後に次局を予約する。
成立予約時に両者の参加枠と開始レート状態を固定し、終局後も参加枠を保持する。
両者のレート更新・適用台帳・ジョブ完了・参加枠解放は同じDBトランザクションで確定する。
claim期限切れで参加枠を解放せず、古い対局の再送で後続対局の枠を変更しない。

## 導入時に詰める事項

Ratingのpool・成立予約・参加枠・開始レート状態の定義と、それぞれの有効期間は別途設計する。
適用台帳の記録内容と一意性の範囲、ジョブの世代更新と隔離後の扱いも別途設計する。
