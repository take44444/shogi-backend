# Googleによる本人確認とアプリケーションのセッションを分ける

Google OpenID Connectの認可コードフローにPKCE S256を組み合わせ、Googleによる本人確認とアプリケーションのログイン状態を分ける。
GoogleのトークンはアプリケーションAPIの認証資格情報に使わず、永続化しない。
独自の不透明なセッションによりサーバー側で失効と期限を管理する代わりに、保護された要求ごとのDB照会を引き受ける。

## ログイン方式の判断理由

バックエンドで認可コードを交換し、Googleとの通信とトークン検証をサーバー側へ集約する。
フロントエンドにGoogleトークンの取扱いを要求しない代わりに、リダイレクトと一時的な試行の保存が必要になる。
PKCE・state・nonceを併用し、コード交換、開始元ブラウザー、IDトークンとの対応をそれぞれ検証することで、クライアントシークレットだけに依存しない。

初回ログインを登録と兼ねるのは、任意の内部IDの登録を許さず、検証済みのGoogle識別子へアカウントを対応付けるためである。
認証情報の保存先を分ける理由は[ユーザーDB分離のADR](0001-separate-user-database.md)に記録する。

## ブラウザー向け構成の判断理由

ユーザー管理はブラウザーのログインとプロフィール操作を対象にHTTPで提供し、内部サービス向けgRPCは対象に含めない。
同一originのブラウザー利用を対象とし、ネイティブアプリや別originの画面との統合は別に設計する。
SameSite=Laxは、GoogleからのトップレベルGETリダイレクトでCookieを利用するために採用する。

Googleの鍵更新を反映するため、起動と各コード交換はdiscovery・JWKSの取得に依存する構成とした。
この選択によりログインは外部通信に依存するが、保存済みセッションの照会にはGoogleへの通信を要求しない。
