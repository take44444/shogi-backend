# 対局時計の設計理由と運用上の制約

## DB を時計の正本にする理由

プロセス内タイマーを正本にすると、再起動時の復元と複数プロセス間の所有権管理が必要になる。
DB に時計と期限を保存し、対局行のロック下で着手と時間切れを判定することで、同じ永続状態に対して勝敗を確定する。
定期処理が遅れても期限を延ばさず、通知だけが遅れる。

操作ごとに履歴から局面を復元する構成は、時計と履歴を異なるバージョンで判断する経路を減らす。
終局時はマッチメイキングの共通ロックを先に取得する必要があるが、通常の着手まで共通ロックで直列化しない。
終局が必要と分かった時点でロックを取り直す理由は、このロック順序と並行性を両立するためである。

## プロダクト上の選択

両者の準備確認がそろった時点を対局開始とし、最初の接続や着手を待たずに時計を進める。
通信遅延、キュー待ち、DB ロック待ちを補償せず、切断中やサーバー停止中も時計を止めない。
これらは対局者の消費時間に含める選択であり、既存のオンライン将棋サービスと同じ運用を保証しない。

表示用フロントエンドはこのリポジトリに含まれない。
時計表示の誤差を勝敗判定には使わず、保存済みの結果に従う。
障害時の無効対局や運営による時計調整は対象に含めない。

## 運用上の検証課題

互換性のない旧版と新版の writer、reader、通知形式を混在させない。
DB 時計の大きな前進や停止は補償できないため、DB 時刻の同期を運用前提とする。
期限の走査間隔と各回の候補数は、本番負荷の測定に基づく値ではない。
長い履歴の復元コスト、ロック保持時間、実際の時計表示、通知遅延は導入先で確認する。
