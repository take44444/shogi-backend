# Google による本人確認とアプリケーションのセッションを分ける

Google OpenID Connect の認可コードフローに PKCE S256 を組み合わせ、Google による本人確認とアプリケーションのログイン状態を分ける。
Google のトークンはアプリケーション API の認証情報に使わず、永続化しない。
独自の不透明なセッションでサーバー側の失効と期限を管理する代わりに、保護されたリクエストごとに DB を照会する。

## ログイン方式の判断理由

バックエンドで認可コードを交換し、Google との通信とトークン検証をサーバー側に集約する。
フロントエンドに Google トークンの取り扱いを要求しない代わりに、リダイレクトと一時的なログイン試行の保存が必要になる。
PKCE、state、nonce を併用し、コード交換、開始元ブラウザー、ID トークンとの対応をそれぞれ検証する。
この検証により、クライアントシークレットだけに依存しない。

初回ログインを登録と兼ねるのは、任意の内部 ID の登録を許さず、検証済みの Google 識別子にアカウントを対応付けるためである。
認証情報の保存先を分ける理由は[ユーザー DB 分離の ADR](0001-separate-user-database.md)に記録する。

## ブラウザー向け構成の判断理由

ユーザー管理は、ブラウザーのログインとプロフィール操作を対象に HTTP で提供する。
内部サービス向け gRPC は対象に含めない。
同じオリジンのブラウザー利用を対象とし、ネイティブアプリや別オリジンの画面との統合は別に設計する。
`SameSite=Lax` は、Google からのトップレベル GET リダイレクトで Cookie を使うために採用する。

Google の鍵更新を反映するため、起動と各コード交換はディスカバリー情報と JWKS の取得に依存する構成とした。
この選択によりログインは外部通信に依存するが、保存済みセッションの照会に Google との通信は必要ない。
